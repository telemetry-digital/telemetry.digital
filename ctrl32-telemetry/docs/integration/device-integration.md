# Connecting any device to ctrl32 telemetry

Integration reference for device makers and for tools that provision devices (such as the ctrl32 editor). It
describes what a device — of any vendor, in any language — needs to do to send data, receive configuration and
commands, and update its firmware. Nothing here requires our client library; the library (`ctrl32-telemetry-c`) is
one implementation of this document. Version: server 0.36.0, protocol 1 (`docs/protocol/device-protocol-v0.1.md`
is the normative specification; this document is the practical subset with tested examples).

## 1. Two transports, one identity

| | MQTT (preferred) | HTTP (for devices without MQTT) |
|---|---|---|
| Endpoint | `telemetry.digital:8883`, TLS 1.2+ (your own instance: `[mqtt] tls_listen`); plain `1883` only inside the intranet profile / VPN | `https://telemetry.digital/api/v1/d/…` |
| Identity | MQTT **username = external id** of the device, **password = device token**, client id any (use the external id) | `Authorization: Bearer <device token>` |
| Protocol | MQTT 3.1.1 or 5, QoS 0/1, keep-alive 30–60 s, clean session | JSON over HTTPS |
| Server → device | subscriptions on `d/{id}/…` (retained shared attributes, commands, console, FOTA target) | polling `GET /api/v1/d/cmd?wait=30` and `GET /api/v1/d/attributes/shared` |

A device exists on the server first (section 2) and has exactly one **external id** (the MQTT username, ≤ 64
characters, e.g. a serial number, DevEUI or `esp32-0b87b0`) and one or more **tokens**. The token is a random
string shown once; the server stores only its hash. Lose it → issue a new one on the device page.

TLS: the public instance uses Let's Encrypt certificates. Embed the roots *ISRG Root X1* and *ISRG Root X2*
(`ctrl32-telemetry-c/examples/common/isrg_roots.h` has both as one PEM bundle; `https://letsencrypt.org/certs/`).
Do not pin the leaf certificate: it rotates every 60–90 days. A device without a correct clock cannot validate
certificates — sync time (SNTP) before the first TLS connection.

## 2. Registering the device on the server

In the UI: **Devices → New device** (external id, name, transport `mqtt` or `http`) → the page shows a **claim
code** (valid 24 h, one use); **Issue token** gives a token directly. Then **Assets →** the asset's datastreams
(keys the device will report) → **Assign** them to the device.

The same over the API with a user or API token that has `device.manage` (+ `data.annotate` for datastreams):

```bash
B=https://telemetry.digital; H='Content-Type: application/json'; A="Authorization: Bearer $API_TOKEN"
curl -s -X POST $B/api/v1/devices -H "$A" -H "$H" -d '{"external_id":"sn-000123","name":"Cold room 3","transport":"mqtt","reason":"new device"}'
#  → {"id":"<uuid>","external_id":"sn-000123","claim":"K7Q2…","claim_valid_to":"…"}
curl -s -X POST $B/api/v1/devices/<uuid>/token -H "$A" -H "$H" -d '{"reason":"factory token"}'
#  → {"token":"<shown once>", ...}
curl -s -X POST $B/api/v1/datastreams -H "$A" -H "$H" -d '{"asset_id":"<asset>","key":"temp","quantity":"temperature","unit":"°C","kind":"gauge","expected_interval":"5 minutes","reason":"new device"}'
curl -s -X POST $B/api/v1/devices/<uuid>/datastreams -H "$A" -H "$H" -d '{"datastream_id":"<ds>","reason":"new device"}'
```

Datastream **keys** are the names the device sends; `kind` is `gauge` (a measured value), `counter` (monotonic),
`state` (discrete) or `event`; `expected_interval` drives gap detection (missing data becomes a visible gap).

### 2.1 Self-provisioning with a claim code

A device that only knows its claim code (printed on a label, typed by an installer, generated by the ctrl32
editor) trades it for a token once:

```
POST https://telemetry.digital/api/v1/provision
{"claim": "K7Q2…", "hw": "esp32-s3", "fw": "1.0.0"}
→ 200 {"device_id": "sn-000123", "token": "<token>", "mqtt": {"host": "telemetry.digital", "port": 8883, "tls": true}, "protocol": 1}
→ 401 {"error": "invalid claim code"}      (used, expired, or the device was revoked)
```

`device_id` is the external id to use as MQTT username. Store the token in non-volatile memory; the claim code is
now spent. Rate limited per IP.

## 3. MQTT

### 3.1 Connection

```
host      telemetry.digital        port 8883 (TLS)        # intranet profile: 1883 plain, only on the LAN/VPN
username  <external id>            password <token>       client id <external id> (any unique string works)
keepalive 30–60 s                  clean session          QoS 1 for data, QoS 0 acceptable for status/console
```

Refused connections (bad id or token, revoked device, disabled organization) return CONNACK reason code 5
(not authorized) and are logged as security events. Publishing to a topic that is not the device's own is refused
by the ACL and logged; nothing is stored.

### 3.2 Topics

All topics of a device live under `d/{external id}/`:

| Topic | Direction | Purpose |
|---|---|---|
| `d/{id}/telemetry` | device → server | measurements (one sample or a batch) |
| `d/{id}/attributes` | device → server | client attributes: `{"fw":"1.4.2","hw":"esp32-s3","model":"…","ip":"10.0.0.12"}` |
| `d/{id}/attributes/request` → `d/{id}/attributes/response` | device ↔ server | ask for shared attributes: `{}` = all, `{"keys":["interval_s"]}` = some |
| `d/{id}/attributes/shared` | server → device, **retained** | configuration set on the server, e.g. `{"interval_s":300,"temp_hi":8.0}` |
| `d/{id}/status` | device → server | heartbeat: `{"online":true,"bat":3.61,"rssi":-71,"up_s":86400,"free":120000,"fw":"1.4.2","buf":12}`; `lat`/`lon` set the position |
| `d/{id}/cmd` | server → device | command: `{"id":"<uuid>","m":"set_interval","a":{"s":60},"exp":1758620600}` |
| `d/{id}/cmd/ack` | device → server | `{"id":"<uuid>","ok":true,"r":{"s":60}}` or `{"id":"<uuid>","ok":false,"err":"unsupported"}` |
| `d/{id}/console/in` → `d/{id}/console/out` | server ↔ device | remote console lines, only while a session is open (`console.enabled` shared attribute) |
| `d/{id}/fota/target` (retained) → `d/{id}/fota/status` | server ↔ device | firmware update announcement and progress (section 6) |
| `v1/devices/me/telemetry`, `v1/devices/me/attributes` | device → server | **ThingsBoard-compatible aliases** — existing ThingsBoard firmware works unchanged |

Subscribe after connecting to `d/{id}/attributes/shared` (retained: the current configuration arrives at once),
`d/{id}/cmd` and, if used, `d/{id}/console/in` and `d/{id}/fota/target`. Wildcard subscriptions are refused.

### 3.3 Telemetry payloads

JSON, UTF-8, at most 64 KiB and 2000 samples per message. Three shapes are accepted, also mixed inside an array:

```json
{"ts": 1758620000, "v": {"temp": 4.2, "rh": 61.0, "door": false}}          ctrl32 shape
{"ts": 1758620000123, "values": {"temp": 4.2, "rh": 61}}                    ThingsBoard shape (ts in milliseconds)
{"temp": 4.2, "rh": 61, "door": false}                                      flat shape: every key is a value
[{"ts": 1758619400, "temp": 4.1, "bf": 1}, {"ts": 1758620000, "temp": 4.2}] batch / backfill
```

Rules the server applies:

- `ts` is Unix time in **seconds**; a value above 10 000 000 000 is taken as **milliseconds** (`tsm` forces
  milliseconds). Without `ts` the server stamps the time of receipt (`time_source = server`). `dt: -300` means
  "300 s before now" for devices without a clock. A device time more than 5 minutes in the future is stored with
  `quality = clock_suspect`.
- `bf: 1` marks a sample replayed from an offline buffer: stored with `quality = backfilled`, it closes the gap and
  alarms found in it are flagged as retrospective.
- `seq` (monotonic message number) is stored with the raw message; reserved for deduplication.
- **Keys** must match `^[a-z][a-z0-9_]{0,31}$`. Foreign keys are normalised first: letters lower-cased, `-`, `.`
  and spaces become `_` (`Temp-1` → `temp_1`, `Batt Level` → `batt_level`). A key that cannot be normalised
  rejects the whole message. Reserved keys (`p ts tsm dt bf seq v values`) are never values.
- **Values** are numbers, booleans (stored as 1/0), strings (≤ 256 bytes) or objects/arrays (kept as JSON, e.g.
  GPS or a state object). `null` is rejected.
- A key with no assigned datastream is **not** stored as an observation: the message is kept as a raw message
  with status `unknown_key` (visible on the device page → Messages, counted in `/metrics`), the other keys are
  stored. Create the datastream and assign it; nothing is created automatically.
- Every message, valid or not, is stored as a raw message (URS F-01); invalid JSON is stored with the error.

### 3.4 Commands, shared attributes, console

- A command arrives on `d/{id}/cmd`; the device answers on `d/{id}/cmd/ack` with the same `id`. Without an ack
  the command expires at `exp` (`ttl_seconds` when it was issued). Commands may need four-eyes approval on the
  server; the device sees only approved ones. Reserved method names of the reference library: `ping`, `reboot`,
  `get_attrs`, `set_interval`, `fota_check`, `console_on`, `console_off`; anything else is yours.
- Shared attributes are the server-side configuration of the device: whenever an operator changes them the server
  republishes the retained document, so a device that reconnects always gets the current one. The device reports
  its own state as client attributes (`d/{id}/attributes`), which the UI shows next to the shared ones.
- Console: while an operator has a session open, the server sets `console.enabled: true` in the shared attributes
  and sends lines on `console/in` as `{"s":"<session>","l":"wifi status"}`; the device answers on `console/out`
  with `{"s":"<session>","t":<unix>,"l":"…"}` (≤ 512 B per line, 5 lines/s). Everything is logged.

### 3.5 Smoke test with mosquitto

```bash
ID=sn-000123; TOKEN=…; H=telemetry.digital
mosquitto_pub -h $H -p 8883 --cafile isrgrootx1.pem -i $ID -u $ID -P "$TOKEN" -q 1 \
  -t d/$ID/telemetry -m '{"temp":4.2,"rh":61}'
mosquitto_sub -h $H -p 8883 --cafile isrgrootx1.pem -i $ID -u $ID -P "$TOKEN" -v \
  -t d/$ID/attributes/shared -t d/$ID/cmd                    # then send a command from the device page
mosquitto_pub … -t d/$ID/cmd/ack -m '{"id":"<command id>","ok":true,"r":{"done":1}}'
```

The repository's `go run ./tools/mqttpub -addr telemetry.digital:8883 -tls -user $ID -token $TOKEN -topic d/$ID/telemetry -payload '{"temp":4.2}' -sub d/$ID/cmd -wait 30`
does the same without mosquitto. On the server: **Devices → the device** shows *connected*, last seen, the
messages with their decode status, the datastream values; `GET /api/v1/observations?datastream_id=…` returns them.

## 4. HTTP

All endpoints take `Authorization: Bearer <device token>` and JSON bodies; `401` = unknown token, `413` = body
too large, `400` = malformed. A device registered with transport `http` receives commands only by polling.

| Method and path | Body | Response |
|---|---|---|
| `POST /api/v1/d/telemetry` | one sample or an array, any shape of 3.3, ≤ 64 KiB | `202 {"accepted":2,"status":"ok"}`; `"status":"unknown_key","unknown_keys":["pressure"]` when some keys have no datastream; `400` invalid JSON or key |
| `POST /api/v1/d/attributes` | client attributes object | `202 {"ok":true}` |
| `POST /api/v1/d/status` | heartbeat object | `202 {"ok":true}` |
| `GET /api/v1/d/attributes/shared` | — | `200 {…shared attributes…}` |
| `GET /api/v1/d/cmd?wait=30` | — | `200 [{"id":"…","m":"set_interval","a":{"s":60},"exp":1758620600}]`; waits up to `wait` s (max 60) for a command; each command is returned once and marked *sent* |
| `POST /api/v1/d/cmd/{id}/ack` | `{"ok":true,"r":{…}}` or `{"ok":false,"err":"…"}` | `200 {"id":"…","status":"acked"}`; `404` when no open command has this id |
| `POST /api/v1/d/fota/status` | `{"fw_id":"…","st":"downloading","pct":42}` | `202 {"ok":true}` |
| `GET /api/v1/d/fota/{fw}/blob` | — | the firmware image (`Range` supported, `X-Checksum-SHA256`) |

```bash
T=…; B=https://telemetry.digital
curl -s -X POST $B/api/v1/d/telemetry -H "Authorization: Bearer $T" -H 'Content-Type: application/json' -d '{"temp":4.2,"rh":61}'
curl -s -X POST $B/api/v1/d/status    -H "Authorization: Bearer $T" -d '{"online":true,"rssi":-60,"bat":3.7}'
curl -s "$B/api/v1/d/cmd?wait=30"     -H "Authorization: Bearer $T"
curl -s -X POST $B/api/v1/d/cmd/<id>/ack -H "Authorization: Bearer $T" -d '{"ok":true,"r":{"s":60}}'
```

A typical HTTP device loop: send telemetry on its interval, send a status every few minutes, poll
`GET /api/v1/d/cmd?wait=30` in between (the request costs nothing while it waits), read shared attributes after
boot and after any command.

## 5. Limits and behaviour to design for

| Item | Value |
|---|---|
| Telemetry message | ≤ 64 KiB, ≤ 2000 samples; attributes ≤ 16 KiB; status ≤ 4 KiB; command ≤ 4 KiB; console line ≤ 512 B |
| Key | `^[a-z][a-z0-9_]{0,31}$` after normalisation; string value ≤ 256 B |
| Timestamps | seconds or milliseconds (auto), UTC; +5 min tolerance before `clock_suspect` |
| Reconnect | exponential back-off 1 s → 5 min; buffer samples offline and replay them with `bf: 1`, oldest first |
| Token | shown once; rotate with the `rotate_token` command (new token in `a`, acknowledge after storing it; the old one stays valid 60 s after the ack); revoking a device disconnects it and blocks the token immediately |
| Failures | wrong credentials and ACL violations are logged as security events; repeated failures from one address are rate limited |
| Not implemented today | CBOR payloads, client certificates (mTLS), firmware transfer in MQTT chunks (use the HTTPS blob) |

## 6. Firmware updates (FOTA)

The server publishes a retained `d/{id}/fota/target` when a campaign targets the device:
`{"fw_id":"…","ver":"1.5.0","hw":"esp32-s3","size":1439232,"sha256":"…","url":"https://…/api/v1/d/fota/<fw>/blob","min_ver":"1.3.0","campaign":"…"}`.
The device checks `hw` and `min_ver`, downloads the blob with its Bearer token (resumable with `Range`), verifies
SHA-256 (and the Ed25519 signature when it carries the author's public key), writes the second slot, reports
`fota/status` (`downloading` with `pct`, `verifying`, `applying`, then `updated` with `ver` from the new firmware,
or `failed`/`rolled_back` with `err`), and must confirm the new version by a heartbeat within `confirm_s` or roll
back. HTTP devices report the same JSON to `POST /api/v1/d/fota/status`.

## 7. Checklist for a new device type

1. External id scheme (serial, MAC-derived, DevEUI) and where the token or claim code lives on the device.
2. Datastream keys, units and kinds; expected interval; which are `state`/`event`.
3. Transport: MQTT/TLS 8883 with the ISRG roots and a synced clock, or HTTP with the loop of section 4.
4. Payload shape (any of 3.3) and batching/backfill while offline.
5. Which commands the device implements and how it acknowledges; which shared attributes it honours.
6. Heartbeat content (battery, RSSI, uptime, free memory, buffered count, `lat`/`lon` if mobile).
7. FOTA: hardware id, slot layout, signature key, rollback.
8. Test: register the device, run the smoke test of 3.5 or the curl lines of 4, check the device page, the messages
   with `unknown_key` and `/metrics` (`ctrl32_ingest_messages_total`).
